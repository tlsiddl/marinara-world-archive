# Marinara World Archive — 단계별 개발 기획서

- **저장소:** `tlsiddl/marinara-world-archive`
- **대상 플랫폼:** Marinara Engine 2.5.2 우선
- **상태:** 기획 초안 v1.2 — 기억 서재 재활용 순서에 맞춘 단계 재배치, 엔진 연결·주입·방 연결 단계 추가
- **원칙:** 독립 확장, 기존 코드 재사용, 작은 변경, 실행으로 검증

## 1. 배경과 책임 구분

World Archive는 롤플레이 세계의 **지속적인 기본 설정**을 직접 추출·관리하는 독립 확장이다. 범위는 NPC 기본 프로필, 장소·공간 구조, 가문·기숙사·조직, 규칙·제도, 반복 일정, 세계관 고유 시스템이다. **완성 이후 기존 NPC 생성 에이전트와 World 에이전트를 사용하지 않는 것을 목표**로 하므로, 단순 설정 저장소가 아니라 해당 에이전트의 신규 정보 추출·수정 제안 기능과 **채팅 프롬프트로의 설정 주입**까지 대체한다.

기존 **기억 서재(Memory Module)** 는 별도 메모리 모듈이다. 실제 발생한 사건, 인물이 겪은 경험, 감정·관계 변화, 비밀·약속, 현재 상태와 회상을 담당한다. 두 모듈은 독립 설치·실행 가능해야 하며, 향후 공통 식별자 및 공개 조회·변경 제안 인터페이스를 통해 상호 보완한다. 기억 서재가 이미 정리한 장면·사건 정보를 추후 연동해 재활용할 수 있도록 하되, 초기 버전에서 기억 서재를 필수 의존성으로 만들지 않는다.

### 핵심 설계 원칙

1. 기존 기억 서재의 데이터와 코드는 승인 없이 변경하지 않는다.
2. 월드별 저장 데이터를 분리하고, 여러 채팅방이 공통 기준 설정을 참조할 수 있도록 한다.
3. 세계 공통 설정과 방별 상태를 구분한다. 다른 방에서 발생한 사건이 공통 세계를 무조건 변경하지 않게 한다.
4. 항목에는 안정적인 `worldId`, `entityId`를 사용하고, 이름과 별칭은 별도 필드로 관리한다. `roomId → worldId` 연결은 1단계에서 도입한다.
5. AI가 추측한 내용과 확정 사실을 구분하며 직접 편집·확정한 설정을 보호한다.
6. 기능을 끄면 불필요한 모델 호출과 작업은 멈추되 기존 저장 데이터는 보존한다.
7. 색인 변경은 영향받는 항목에만 적용하고, 임베딩 실패가 일반 저장·검색 기능을 중단시키지 않도록 한다.
8. 리팩터링 및 재사용은 실제 의존성과 테스트를 조사한 뒤 결정한다.
9. **NPC/World 에이전트 대체는 필수 제품 목표**다. AI 기반 NPC 프로필 생성·갱신과 세계 설정 추출·변경 제안을 필수 기능으로 제공하며, **얇은 수직 슬라이스(2단계)로 먼저 검증**한다.
10. 가능하면 한 번의 AI 분석 결과에서 인물·장소·조직·규칙·일정 후보를 분류해 중복 모델 호출을 줄인다. 추출·승인 로직과 데이터 저장은 분리한다.
11. 기존 에이전트 코드는 선택적으로 참고할 수 있지만 실행·설치·코드 재사용을 필수 조건으로 두지 않는다.

### 1차 개발 제외 범위

- **기존 마리나라 로어북 가져오기**
- 기존 로어북 자동 동기화·자동 수정
- 기억 서재 직접 수정 및 실제 실시간 양방향 동기화
- NPC의 자율 행동을 생성하는 시뮬레이션 엔진
- 매 메시지마다 전체 세계관을 재분석하는 AI 처리

## 2. 데이터 및 시스템 개념

### 2.1 세계관과 채팅방

하나의 세계관은 고유 ID, 명칭, 설명, 시대·배경, 정보 항목, 변경 이력을 가진다. 여러 채팅방에서 같은 기준 설정을 조회할 수 있다. **한 채팅방은 하나의 세계관을 참조**하며(`{ roomId, worldId }`), 추출 제안은 연결된 세계관으로 들어간다. 채팅방별로 달라진 정보는 공통 세계관을 바로 덮어쓰지 않으며, 추후 방별 오버레이 또는 변경 제안 방식으로 확장한다.

### 2.2 엔티티 유형

| 유형 | 예시 정보 |
| --- | --- |
| 인물 | 이름·별칭, 명시된 신상, 외형, 성격, 배경, 소속, 가족·관계 |
| 장소 | 이름·별칭, 위치, 공간 구조, 입구·출구, 연결, 용도·제약 |
| 집단 | 가문, 기숙사, 학교, 조직, 구성원, 위계와 역할 |
| 규칙 | 법칙, 마법·능력 체계, 제도, 관습, 점수·계급 |
| 일정 | 수업 시간표, 반복 행사, 학사 일정, 정기 활동 |
| 사용자 정의 | 세계관 고유 확장 항목 |

관계는 가능한 경우 텍스트에 다른 이름을 반복하는 대신 안정적인 엔티티 ID를 참조한다. 동명이인과 시대가 다른 인물은 이름만으로 자동 병합하지 않는다. 엔티티 `fields`는 자유 객체로 두지 않고 **타입별 검증 스키마**를 둔다. 관계의 `validFrom/validTo`는 **작중 시간** 기준으로 정의한다.

### 2.3 변경 상태

확정 / 자동 추출 후보 / 검토 대기 / 충돌 / 대체됨 / 삭제됨을 구분한다. 각 변경은 발생 시각·주체·원문 근거·이전 값·새 값·승인 상태를 추적할 수 있도록 계획한다. 직접 확정한 필드의 자동 덮어쓰기는 금지한다.

### 2.4 프롬프트 주입

World Archive는 자체 매크로(`{{세계}}`/`{{world}}`)로, 채팅방에 연결된 세계관의 설정을 **글자 예산 안에서** 프롬프트에 넣는다. 주입 대상은 처음에는 확정 엔티티 전체(예산 내)이고, 5단계에서 "방에 등장한 인물·장소 + 검색 상위 N"으로 좁힌다. 기억 서재의 `{{기억}}`과 같은 정보를 중복으로 넣지 않도록 역할 경계(고정 설정 vs 경험)를 지킨다.

## 3. 기억 서재 코드 재활용 방침

### 3.1 재활용 대상과 배치 단계

v1.1은 `vectors`·`aliases`·`names`·`places`·`features`·`backup`만 재사용 후보로 보고 검색·이력 단계를 앞에 두었다. 그러나 기억 서재(`refactor/modular`, `e873fd1` 정적 조사)에는 **엔진 연결·주입·AI 추출이라는 더 큰 재사용 대상**이 있으므로, 재활용 가치가 큰 순서대로 단계를 앞당긴다.

| 기억 서재 파일·함수 | 이미 해결한 문제 | 배치 단계 |
| --- | --- | --- |
| `marinara-memory-runtime.cjs` | `module.registerHooks`로 엔진 파일을 쓰지 않는 메모리 내 패치. 2.5.1/2.5.2 대상, 앵커가 정확히 1회일 때만 적용(fail-closed) | 0.5·1 |
| 같은 파일의 `macro` 패치 | `{{기억}}` 매크로 치환으로 프롬프트 주입 | 0.5·1 |
| 같은 파일의 `app` 패치, `service.cjs` `attach` | Fastify 라우트 등록(접두사 분리)·훅 | 1 (`feature/phase-1-foundation` 초안에 일부 반영) |
| `service.cjs` `renderMemorySource`·`assembleMemorySource` | 글자 예산 안에서 주입 텍스트 조립 | 1 |
| `install.ps1`/`install.sh` | 마리나라 폴더 탐지, 이전 버전 롤백, 실행 파일 생성 | 1 |
| `service.cjs` `askModel`, `scenes.cjs` `buildScenePrompt`·`parseScenesReply`·재시도 | 모델 호출·구조화 출력 파싱·실패 재시도 | 2 |
| `scenes.cjs` `nextSlice` | 마지막 처리 위치 이후만 분석(중복 분석 방지) | 2 |
| `names.cjs` | 이름 변경 미리보기·적용·되돌리기 패턴 | 4 |
| `conflicts.cjs` | 모델 호출 없는 사실 충돌 판정, 사용자 판정(keepA/keepB/both/dismissed) | 4 |
| `vectors.cjs` | 해시 기반 부분 색인, 벡터 직렬화·유사도 | 5 |
| `aliases.cjs`, `places.cjs`, `features.cjs`, `backup.cjs` | 정규화·보호·설정·백업 검증 원칙 | 해당 단계에서 원칙만 참고 ([PHASE-0-RESEARCH.md](PHASE-0-RESEARCH.md) §2) |

### 3.2 재활용 방식

1. **복사 이식(vendoring), 공유 의존 금지.** 기억 서재를 `require`하지 않는다. 필요한 함수만 `world-archive/lib/vendor/`로 복사하고 파일 머리에 출처 커밋·원본 함수명을 적는다. 독립 설치 원칙을 유지한다.
2. **통파일 복사 금지.** `service.cjs`(약 5,700줄)·`scenes.cjs`(약 4,100줄)는 `chatId` 기준 저장·방 삭제 처리와 결합돼 있다. 순수 함수(파싱, 슬라이스, 예산 자르기, 충돌 판정)만 떼어 오고, 숨은 `store` 구조·전역 설정 의존을 함수 단위로 확인한다.
3. **같은 저자의 코드**이므로 라이선스 부담은 낮지만, 서드파티 의존성은 확인한다.
4. **식별자 분리:** `globalThis.__marinaraWorldArchive`, 매크로 `{{세계}}`/`{{world}}`, API 접두사 `/api/world-archive`, 데이터 디렉터리를 모두 기억 서재와 다르게 한다.

### 3.3 두 로더의 공존 위험

기억 서재는 `start-memory.bat`으로 preload 로더를 붙여 실행한다. World Archive도 같은 방식이면 **사용자는 두 실행 방식 중 하나만 고를 수 있다.** 또 두 로더가 같은 파일(`app.js`의 `app.decorate("db", db);`, `macro-engine.js`)을 같은 앵커 기준으로 패치한다.

- 기억 서재 패치는 앵커 **뒤에 삽입**하므로 앵커는 1회로 남는다. 이론상 두 번째 패치도 적용 가능하나 **실측 전에는 가정하지 않는다.**
- 해결 후보: (a) 두 로더를 모두 `--require`하는 통합 실행 파일, (b) 각 로더가 서로를 감지해 같은 `registerHooks` 체인에 합류.
- 기억 서재 코드를 수정하지 않고 해결해야 하므로 **0.5단계에서 가장 먼저** 검증한다.

## 4. 개발 단계

### 0단계 — 기존 코드 조사 및 상세 설계

**목표:** 구현에 앞서 재사용/수정/신규 작업 범위와 위험을 구분한다.

- 기억 서재 `main` 및 `refactor/modular` 구조와 의존성을 살핀다. 진행 중인 리팩터링을 임의로 변경하지 않는다.
- 런타임 로더·주입·추출 파이프라인을 포함해 재사용 가능성을 분석한다(§3.1).
- 기존 World/NPC 에이전트의 추출 구조는 **참고할 자료가 확보된 경우에만** 검토한다. **기존 로어북 가져오기 기능은 설계·구현하지 않는다.**
- AI 대체 기능의 입력·출력 계약과 한 번의 분석에서 후보를 분배하는 구조를 설계한다.
- 자료 구조, 식별자 규칙, 기능 경계, 모델 호출 지점, 재사용 라이선스·의존성을 문서화한다.

**산출물:** 재사용 가능성 표, 신규 코드 목록, 데이터/API 설계 초안, 위험·호환성 검토 및 테스트 계획.

**완료 기준:** 실제 코드 근거를 갖춘 변경 지도가 있고 각 영역의 소유권이 확정됨. **0단계는 제품 기능 구현을 하지 않는다.**

### 0.5단계 — 엔진 연결 스파이크 (버리는 코드 허용)

**목표:** 이후 모든 단계가 의존하는 엔진 연결 방식과 두 모듈 공존을 실측한다.

- 기억 서재 런타임 로더를 참고해 `{{세계}}` 매크로가 고정 문자열을 돌려주게 한다.
- `/api/world-archive` 아래 확인용 라우트 하나를 등록한다.
- 격리된 2.5.2에서 **단독 실행**과 **기억 서재와 동시 실행**을 모두 확인한다(§3.3).
- 확장 재설치·업데이트 시 데이터 디렉터리가 보존되는지 확인한다.

**완료 기준:** 두 모듈 동시 실행에서 `{{기억}}`, `{{세계}}`가 모두 치환되고 각자의 API가 응답함. 실패하면 원인과 대안(통합 실행 파일 등)을 보고하고 멈춘다.

### 1단계 — 독립 골격 + 방·세계관 연결 + 주입

**목표:** 기억 서재 없이 Marinara에서 독립 실행·저장하고, 설정이 실제 채팅 프롬프트에 들어간다.

- 0.5단계 로더를 정식화. 설치·업데이트·롤백 스크립트는 기억 서재 설치 스크립트를 참고해 작성.
- 세계관 생성·선택·이름 변경·삭제, 원자적 저장(임시 파일→교체), 스키마 버전, API·오류 처리.
- **`roomId → worldId` 연결** 저장과 UI.
- `{{세계}}`가 연결된 세계관의 엔티티를 글자 예산 안에서 출력(`renderMemorySource`의 예산 처리 참고).
- 기존 마리나라 API와 엔진·UI 동작에 대한 영향 확인.

**참고:** `feature/phase-1-foundation` 브랜치의 초안(저장소·Bearer 토큰 API·opt-in `app.js` preload·Shadow DOM UI·단위 테스트)은 이 단계의 저장·API 부분에 해당한다. 매크로 주입·방 연결·설치 스크립트는 아직 없다.

**완료 기준:** 손으로 넣은 설정이 재시작 후 유지되고, 연결된 방의 프롬프트에 들어간다. 기억 서재 유무와 무관하게 작동하며 독립 설치·제거가 가능하고 기존 데이터에 영향 없음.

### 2단계 — 인물 수직 슬라이스 (NPC 에이전트 대체 최소판)

**목표:** 추출 → 제안 → 승인 → 주입의 전체 경로를 인물 한 종류로 먼저 완성한다.

- 엔티티 타입은 **인물만**: 이름·별칭·필드·`status`·`provenance`, 목록·상세·편집 UI.
- 추출 트리거: **수동 버튼 + 선택적 장면 단위**. `nextSlice` 방식으로 마지막 처리 위치 이후만 분석.
- `askModel`·프롬프트 빌드·파싱·재시도 이식. 출력은 처음부터 **다중 타입 스키마**(person/place/group/rule/schedule)로 받되, 이 단계에서는 인물만 저장하고 나머지 후보는 버리지 않고 `pending`으로 보관.
- 기존 인물 매칭은 **코드에서** 이름·별칭 정확 일치로 먼저 수행하고, 매칭된 인물의 현재 값만 프롬프트에 넣는다(호출 1회 유지).
- 제안 → 승인/거절/수정 UI, 원문 근거 연결, 확정 필드 잠금.
- 확정되지 않은 추측은 공식 설정으로 자동 저장하지 않음.

**완료 기준:** 기존 NPC 에이전트 없이 새 NPC가 제안·승인되어 `{{세계}}`로 주입된다. 같은 원문 재처리 시 중복 제안이 없고, 모델 호출 수·토큰을 측정해 기록한다.

### 3단계 — 엔티티 타입 확장 + 관계 (World 에이전트 대체 완료)

**목표:** 세계 설정 전반의 CRUD와 추출을 제공한다.

- 장소·집단·규칙·일정·사용자 정의 항목. 타입별 필드 검증 스키마.
- 관계는 `targetEntityId` 참조, 소속·구성원·장소 연결. 삭제 시 참조·영향 확인.
- 기본 설정과 사건·일시적 상태를 구분하는 데이터 모델.
- 2단계에서 보관한 비인물 `pending` 후보를 해당 타입으로 처리. NPC와 세계 설정을 **한 번의 분석**에서 함께 처리하는 경로 검증.

**완료 기준:** 각 엔티티를 CRUD하고 참조 관계를 보존하며, 재시작·삭제·잘못된 입력에도 데이터가 안전함. 기존 World 에이전트 없이 세계 설정 신규/변경 제안이 동작함.

### 4단계 — 변경 이력·충돌·사용자 편집 보호

**목표:** 수동 수정과 확정 설정을 안전하게 유지한다.

- 필드별 변경 이력·잠금, 수정 전후 비교, 삭제 이력·되돌리기(`names.cjs` 패턴 참고).
- `conflicts.cjs`의 무호출 충돌 판정을 엔티티 필드 대상으로 이식. 동일 항목 후보, 충돌 후보, 검토 대기 상태와 승인 처리.
- 시간에 따라 정상적으로 변한 사실(작중 시간 `validFrom/validTo`)과 실제 모순을 구분하는 기준.
- AI 추정값 또는 유사도만으로 자동 덮어쓰기·병합 금지.

**완료 기준:** 사용자가 확정한 필드를 보호하고 충돌·중복·되돌리기 시나리오 통과.

### 5단계 — 검색 고도화 (벡터는 선택)

**목표:** 많은 설정에서 정확한 항목을 찾고, 주입 대상을 좁힌다.

- 이름/ID/별칭 정확 일치, 제목·내용·분류 키워드, 구조적 필터를 먼저 제공.
- 엔티티 수가 주입 예산을 넘는 세계관에서만 벡터 의미 검색 사용(`vectors.cjs` 순수 계산 이식, 독립 색인·부분 재색인·실패·재시도).
- 주입 선별을 "방에 등장한 인물·장소 + 검색 상위 N"으로 개선.

**완료 기준:** 동명이인·별칭·유사 표현의 검색 테스트를 통과하고, 임베딩을 꺼도 1~4단계 기능과 키워드 검색이 정상 작동함. 정확한 이름 일치를 벡터 점수만으로 뒤집지 않음.

### 6단계 — 기억 서재 연동 **준비**

**목표:** 실제 기억 서재를 수정하지 않고 추후 연결할 안정적인 인터페이스를 제공한다.

- `worldId`/`entityId`/`roomId` 연결 계약 문서화.
- 인물·장소·별칭·관련 설정 조회 API, 외부 모듈용 변경 제안 API와 인증·권한 규칙.
- 버전 호환성, 오류 처리, 연동 대상이 꺼져 있을 때의 동작.
- 통합 검색 결과에 ID·원본 출처·확정 상태·적용 범위 포함.
- 기억 서재 장면 정리 결과를 추출 입력으로 받는 계약.
- **주입 중복 방지 계약:** 같은 인물 정보를 `{{기억}}`과 `{{세계}}`가 모두 넣지 않도록 역할 경계 명시.

**완료 기준:** 독립 실행을 유지하면서 외부 클라이언트가 공개 인터페이스로 정보를 안전하게 조회할 수 있음.

**주의:** 실제 기억 서재의 시뮬레이터 모드 구현, 기억 주입 조정 및 양방향 동기화는 **본 단계의 범위 밖**이며 별도 승인·프로젝트에서 수행한다.

### 7단계 — 종합 검증·릴리스

**목표:** 실제 엔진에서 데이터와 성능을 보호하며 배포할 수 있음을 확인한다.

- 세계관 CRUD, 관계·별칭, 이력·잠금, 검색·임베딩 오류와 복구.
- 외부 NPC/World 에이전트 없이 추출/변경 제안·주입이 동작하는지, 동일 원문의 중복 AI 호출·중복 후보 생성 여부.
- 백업·복원, 재시작, 설치·업데이트·제거, 오래된/손상된 파일 보호.
- 다수 NPC·대량 설정에서 검색 지연, 메모리, 모델 호출 수, 주입 글자 수 측정.
- Marinara Engine 2.5.2 격리 통합 검증, 기억 서재와 단독/동시 설치 검증.
- 브라우저·모바일 및 실제 사용할 배포 환경의 권한/프록시/Origin 검증.
- 배포 전 백업과 롤백 절차 확인.

**완료 기준:** 기능·호환성·성능·데이터 복원 검증을 문서화하고 사용자 승인 후에만 배포.

## 6. 브랜치·승인·중단 조건

`main`은 안정 코드와 문서, `feature/*`는 단계별 작업 브랜치다. 승인 시점·중단 조건·기록 방식은 [AGENTS.md](../../AGENTS.md)를 따른다.

## 7. 최종 성공 기준

세계관 설정집이 독립적으로 설치·실행되며, 인물·장소·조직·규칙·일정의 안정적인 저장과 정확한 검색을 제공하고, 연결된 채팅방의 프롬프트에 필요한 설정을 예산 안에서 주입한다. **기존 NPC 생성 에이전트 및 World 에이전트 없이도** NPC 프로필과 세계 설정의 신규 추출·갱신 제안이 가능해야 한다. 사용자 확정 설정을 보호하고, AI는 검토 가능한 변경 후보만 제안한다. 향후 기억 서재와 연결할 수 있지만 연결을 강제하지 않으며, 동시 설치 시 서로의 동작을 깨지 않는다. 불필요한 코드 재작성과 중복 모델 호출 없이 유지보수 가능한 구조를 우선한다.
